Architecture research · 10 October 2026

A modular, extensible desktop client on the OpenCode v2 engine

This study reads the OpenCode v2.0.25 source and the current OpenChamber source, then recommends how to build an independent desktop client that keeps the engine intact and can grow a community ecosystem of themes, views, commands, integrations and workflows.

01Executive summary

Recommended direction

Build a hybrid architecture, in stages. An Electron app whose main process runs a thin engine gateway for discovery, credentials and the single event stream. A pure adapter package is the only code that knows OpenCode wire shapes. A small application core of contribution registries, commands, settings and a read-only store sits above it. Every product feature is a first-party module built on an internal SDK with lint-enforced boundaries. Third parties get a separate, smaller, versioned extension API: declarative packages first, sandboxed iframe extensions second, privileged local services last. Agent-side capabilities such as new tools go into OpenCode engine plugins, which talk to their GUI half over OpenCode's own plugin RPC. The UI is React. The gateway is written host-neutral, so the same code can later run in a server for the web and mobile versions.

Findings that shape the design

  • VerifiedOpenCode already builds its own app this way. In v2.0.25, every desktop and web feature that is not the core shell is a built-in GUI extension on a typed SDK (gui-extensions). That SDK is private, landed between v2.0.20 and v2.0.22 (1 to 4 October 2026), and has no sandbox. Its archive installer evaluates bundles as trusted code and is refused in packaged builds "until installs have a trust model". It is a strong design reference and a strategic signal. It is not a platform you can build on today.
  • VerifiedThe engine is one shared background service per user. opencode serve --service registers itself in ~/.local/state/opencode/service.json. The official desktop asks for its exact bundled version and replaces a running service of any other version. A client that does the same starts a version war with the official app.
  • VerifiedThe event stream is volatile by contract. One SSE stream for all projects, no replay, a 4,096-event buffer per subscriber, and overflow kills the stream. The client must be built as snapshot plus deltas with deliberate resync.
  • VerifiedThe public contract is documented. V2_HTTP_API_AUDIT.md classifies all 141 operations as keep, change, remove or experimental. That gives you a defensible line between what to depend on and what to wrap behind feature flags.
  • VerifiedChurn is real but has settled. 27 releases in 27 days. v2.0.0 to v2.0.10 renamed every operation and removed endpoints. v2.0.10 to v2.0.26 has been additive. Request bodies reject unknown fields, so a newer client can break against an older engine.
  • InferredA second engine process on the same database is unsafe. Session execution is process-local with restart-recovery claims, and upstream code comments call two services on one database a hazard. "Run my own private engine" is only safe with a separate database, and a separate database means separate session history.
  • VerifiedWhoever holds the engine credential can approve agent actions. The official app's auto-approve is a client-side setting. Extensions must never see the credential or answer permission requests, and "send a prompt" has to be treated as a high-risk capability.
  • VerifiedOpenChamber shows both what works and what to avoid. It has a clean wire-translation layer, a compatibility gate and capability-gated sandboxed extensions. It also reads CLI-private files and writes a row into OpenCode's SQLite database to re-arm a migration, and its core features are not built on its own extension SDK.

Build first

  • Engine gateway with join-never-replace policy and resync, written host-neutral so a server can run it later
  • Adapter package and client-owned domain model
  • Core registries: commands, keybindings, menus, panels, settings, themes
  • Internal module manifest, contracts and lint boundaries
  • Declarative theme format and design tokens
  • Compatibility CI across two engine versions

Defer until there is demand

  • Third-party code runtime (until the core contribution model has stabilized)
  • Marketplace, signing and publisher verification
  • Privileged local services for extensions
  • Extensions rendering inside the timeline
  • Web and mobile, until the desktop works (section 6.10)
  • Any engine abstraction beyond OpenCode

Decisions recorded

  • DecidedDesktop first. Web and mobile follow once the desktop works, reusing the same core (6.10).
  • DecidedUsers install OpenCode themselves. No bundled binary, so the client supports a version range (8.6).
  • DecidedReact for the UI (ADR-006, 6.11).
  • DecidedA curated git index you maintain as the first registry (ADR-013).
  • DecidedCompanion engine plugins: the client shows the config line and checks it was added. It never edits engine config silently (7.12).
  • DecidedContribute upstream by opening issues for four engine improvements, without waiting on them (8.8).
  • RecommendationProduct name: Mortise, with Binnacle as the alternate (section 13).

2.2 Engine process model

  • VerifiedOne background service per user and release channel. opencode serve --service writes service.json under $XDG_STATE_HOME/opencode/ (falling back to ~/.local/state/opencode/) with mode 0600. The file holds instance id, version, URL, pid and a private password. Every 5 seconds the service re-reads the file and shuts itself down if another service has replaced the registration. cli/src/services/service-registration.ts
  • VerifiedFixed default port. Stable channels listen on 0xC0DE (49374), so a second contender fails to bind and backs off. Other channels hash to their own port and registration file. cli/src/services/service-config.ts
  • VerifiedDiscovery API. @opencode/client/service exports discover() (find a ready, compatible service without starting one), ensure() (start opencode serve --service if missing) and stop() (with optional terminal handoff). Its comment calls the registration file "the complete discovery contract". client/src/promise/service.ts
  • VerifiedVersion replacement. ensure({ version }) takes an exact string or a predicate. If the running service fails it, decide() returns replace, and ensure stops that service and starts its own. A 404 on GET /api/info marks a service incompatible rather than older. client/src/service-probe.ts
  • VerifiedThe official desktop pins. On first connect it passes its bundled CLI version, so it replaces any other running version. Reconnects pass no version and adopt whatever is running. desktop/src/main/service/background-service.ts
  • VerifiedPersistence. The engine database is <data dir>/opencode.db. Other channels get a channel-specific name, and OPENCODE_DB overrides it. cli/src/database-path.ts
  • InferredTwo engine processes must not share a database. The desktop explains its fixed port by saying that with port 0 "two services could boot against the same database". The root AGENTS.md describes session execution as process-local, with write-ahead execution claims that a restarted process resumes. Two processes on one database could each drain or resume the same session. Not tested.
Implication

RecommendationJoin the user's service by default and never replace it unasked. If you need isolation, run a private engine with its own OPENCODE_DB and accept separate history. Section 8 turns this into a connection policy.

2.3 Client protocol

  • VerifiedHTTP and JSON under /api. The API is defined as an Effect HttpApi in protocol, served live at /openapi.json (server/src/routes.ts), and committed as protocol/openapi.json with 141 operations. The document's own info block says version 0.0.1, "Experimental HttpApi surface".
  • VerifiedAuthentication. HTTP Basic with username opencode and the service password. Pairing works like this: POST /api/pair issues a short-lived single-use code, and /auth/connect/:code exchanges it for a session token. The token is HMAC-signed with a key derived from the password, lives 30 days, and is revoked when the password rotates. server/src/auth.ts
  • VerifiedCORS allowlist. http://localhost:*, http://127.0.0.1:*, oc://renderer, Tauri origins, https://*.opencode.ai, plus a cors list from service config. Requests with no Origin header pass. server/src/cors.ts
  • VerifiedLocation scoping. Most routes take location[directory]. One server serves many directories and initializes each lazily on first use. server/src/location.ts
  • VerifiedTerminals. A WebSocket at /api/pty/{id}/connect, gated by a one-time connect token. The generic HTTP client does not cover it.
  • VerifiedStrict request bodies. Bodies such as session.prompt declare additionalProperties: false, so an older engine rejects any field it does not know.
  • VerifiedTyped errors per endpoint, for example SessionNotFoundError and InvalidCursorError. The audit replaced many nullable responses with typed 404s. protocol/src/errors.ts
Implication

InferredAn Electron renderer on a custom scheme such as app:// will be refused unless the user's shared service config lists it. Adding it would mean editing someone else's config. Route engine traffic through the main process, which sends no Origin header and keeps the password out of the renderer. Do not reuse oc://renderer, which belongs to the official app.

2.4 Events and streaming

  • VerifiedOne stream for everything. GET /api/event is SSE across all locations. The first event is server.connected, and a heartbeat comment arrives every 15 seconds (server/src/handlers/event.ts). Each subscriber gets a dropping queue of 4,096 encoded events, and overflow fails that subscriber (server/src/event-feed.ts). The protocol describes the stream as "Volatile by contract: a slow consumer overflows and fails the stream, and events during disconnection are missed." It sends no id: lines and has no Last-Event-ID replay. protocol/src/groups/event.ts
  • VerifiedEnvelope. Each event has id (evt_…), type, created, data, and optionally location and metadata. Durable events add durable: { aggregateID, seq, version }. Ephemeral events, which include all streaming deltas, do not. schema/src/event.ts
  • VerifiedPublic inventory. EventManifest.ServerDefinitions lists the events that may appear on the public stream: session lifecycle, inbox, execution, steps, text and reasoning deltas, tool input, calls, progress, success and failure, retry, compaction, revert, permissions, forms, terminals, shells, MCP, VCS, and plugin RPC events named rpc.*. schema/src/event-manifest.ts
  • VerifiedThe reference client's recovery. 2 s connect timeout, 45 s idle watchdog, 1 s reconnect delay, events applied in 10 ms batches, and a forced resync on the online event or when the page returns after 20 s of quiet (client/src/solid/connection.ts). On every server.connected it refetches active sessions, location, VCS and projects, and revalidates cached reads one at a time so an older response cannot overwrite a newer one (client/src/solid/data.ts).
  • VerifiedNo session status event. Running and idle are derived from session.execution.* plus the GET /api/session/active snapshot.

2.5 Sessions, execution and concurrency

  • VerifiedAdmission is separate from execution. session.prompt durably enqueues an inbox item, then wakes the runner. resume: false admits without running. Delivery is steer (default, delivered at the next step boundary) or queue (delivered when the session would go idle). Pending items can be cancelled or switched between modes. (Root AGENTS.md, V2 Session Core; audit groups 5 and 7.)
  • VerifiedIdempotent retries. The prompt body accepts an id matching ^msg_. Reusing an id for the same session and type returns the first admission, so a client can retry safely with ids it generates itself.
  • VerifiedConcurrency and recovery. Different sessions run concurrently. Resumes of the same session join one run. session.interrupt stops the active run. After a restart the engine resumes sessions that still hold an execution claim.
  • VerifiedOther operations include fork (optionally before a message), staged revert with commit or clear, compact, shell, command, synthetic input, move, background, switch agent or model, diff, context, and one-off generation.

2.6 Permissions, forms, configuration and credentials

  • VerifiedPermissions. Pending requests are listed per session or globally. A reply carries decision: "once" | "always" | "reject". Saved permissions can be listed and removed, and session rules change through session.update.
  • VerifiedApproval is a client power. The official app's auto-approve is a client-local setting that answers every permission.asked on a connection, and it sweeps pending requests on reconnect because the stream does not replay them. app/src/session/requests/auto-approve.ts
  • VerifiedForms are questions the engine asks the user, with typed answers, reply and cancel.
  • VerifiedConfiguration is readable (GET /api/config returns documents and directories) but not writable through the stable API. The only write route is experimental and accepts only shell.
  • VerifiedCredentials and integrations support list, create, update, remove, activate, OAuth and command-based connection flows.
  • VerifiedEngine plugins can be listed, checked and updated, but there is no install endpoint. They are declared in the plugins config key as a package name plus options. schema/src/config/plugin.ts

2.8 Extension points that already exist

Engine plugins

Verified@opencode/plugin plugins run in-process inside the engine. They register transform hooks for agents, commands, integrations, MCP, models, providers, references, skills, tools, VCS and web search, plus runtime hooks for the AI SDK, session context just before dispatch, and retry decisions. They can add executable tools with schema-typed input and output. Plugins share the host's effect instance and run with full engine privileges. plugin/src/README.md

Plugin RPC: the official bridge between a plugin and a client

VerifiedA plugin defines methods and events with portable schemas (Standard Schema or JSON Schema). Clients call POST /api/rpc/{rpcID}/{method}, and plugin events arrive on the main stream as rpc.*. System errors are rpc.unavailable, rpc.method_not_found, rpc.invalid_input, rpc.invalid_output and rpc.internal. schema/src/rpc.ts

Verifiedplugin-browser is the worked example. The engine plugin owns the tools, invocation scope and permissions. The desktop owns tabs, CDP and captures. They connect over authenticated RPC with a versioned attach, a readiness event, and an explicit rule that lost calls are never replayed. This is the template for any extension that has both an agent half and a GUI half. plugin-browser/README.md

The official GUI extension SDK

Verifiedgui-extensions says that "every feature of the desktop and web app that is not the core shell is an extension". Built-ins include context, btw, debug, terminal, file, review, details, browser, pairing, updater, SSH, WSL and Microsoft Office. gui-extensions/README.md

  • Manifest: Extension.define({ id, legacy, os, provides, uses, requires, stores, i18n }), read before any code loads.
  • Tokens: Registry (lists others contribute to), Contract (in-process APIs between extensions), Ipc (schema-typed main-to-window contracts).
  • Registries: Command, MenuItem, Panel, SettingsPage, Server, LinkHandler, TitlebarItem, Slot, Style, MenubarItem. gui-extensions/src/sdk/registries.ts
  • Liveness: optional dependencies arrive as Live<T>: pending, active, or inactive (restarting, disabled, failed, blocked). Required dependencies block setup.
  • Stores: Store.global, Store.session and Store.main, declared up front with migrations from older keys.
  • Discipline: the host never names an extension, extensions import only each other's contract.ts, the linter bans raw effects, app imports and module-level state, and a test boots the graph with each optional provider disabled.

VerifiedGroundwork for installable .ocdx archives exists. The manifest schema is opencode.gui-extension/1 with CommonJS bundles. The desktop evaluates main bundles with new Function against a shared module map, commented "Installed extensions are trusted code the user chose to install". Renderer bundles are not loaded yet, and the IPC handler refuses install, enable and reload in packaged builds "until installed extensions have a trust model". desktop/src/main/extension/module.ts desktop/src/main/ipc-handlers/extensions.ts

VerifiedThe system is new. It is absent at v2.0.20 and present at v2.0.22, from commits f406d93 (2026-10-01, "move GUI features into built-in extensions") and 0048c97 (2026-10-04, "typed composition and lifetime primitives").

Themes, terminal UI plugins and ACP

  • VerifiedThe desktop theme format is JSON with light and dark variants, each built from nine seed colors or a palette, plus token overrides. 36 themes ship. ui/src/theme/desktop-theme.schema.json
  • VerifiedThe terminal UI has its own plugin entry, @opencode/plugin/tui.
  • VerifiedThe CLI implements the Agent Client Protocol through @agentclientprotocol/sdk. It is an editor-style integration surface, narrower than the HTTP API. cli/src/acp/agent.ts

2.9 How the official clients use the engine

  • VerifiedThe app is multi-server. Its initial server is the page origin when opencode serve hosts it, or none. Users add servers, connect with a password, or paste or scan a pairing link. app/README.md
  • VerifiedThe desktop keeps credentials in main. The renderer reaches main only through window.electron and a MessagePort RPC client, and windows run with contextIsolation, sandbox: true and no Node integration. desktop/AGENTS.md desktop/src/main/windows/appearance.ts
  • VerifiedThe desktop guidance prefers SQLite over plain files for persistence, citing Windows EPERM problems. The desktop keeps its own database, separate from the engine's.

03OpenChamber analysis

3.1 What it is

  • VerifiedSurfaces and stack. MIT-licensed. One React UI (packages/ui) is shared by Electron, web and PWA, VS Code and Capacitor mobile. A Node server in packages/web sits between the UI and OpenCode. Electron starts that backend in-process, "never as a sidecar", and packaged builds load the UI from openchamber-ui:// with the loopback server as the API. openchamber/AGENTS.md
  • VerifiedEngine dependency. It talks to OpenCode through @opencode/client pinned at 2.0.25, and confines wire shapes to packages/ui/src/lib/opencode/.
  • VerifiedEngine lifecycle. Three installation kinds: managed, external and bundled. The managed path spawns opencode serve --hostname --port with its own password rather than joining the shared service. A gate requires OpenCode 2.0.20 or newer and reports compatible, incompatible or unavailable. web/server/lib/opencode/lifecycle.js compatibility.js
  • VerifiedEvents. The server holds one upstream SSE reader and fans events out to browsers over WebSocket. It keeps a bounded replay buffer of 2,048 events or 8 MiB and merges streaming deltas within 50 ms. It synthesizes session status from execution events, and one module maps v2 events into its own vocabulary. web/server/lib/event-stream/DOCUMENTATION.md
  • VerifiedExtensions. @openchamber/sdk defines "guests" with a package.json manifest (apiVersion: 1, an engines floor). Contributions are panel, background, attach, page, status section, file editors, actions, slash commands, declarative tool-call renderers, integrations and a local service. Capabilities are approved once at install and enforced on the server. Guests run in sandbox="allow-scripts" iframes under a CSP that blocks all network access. Network calls go through the host, which injects credentials the page never sees. sdk/README.md sdk/src/frame-policy.ts

04Requirements and architectural constraints

4.1 Requirements from the brief

  • R1 Engine independence. The engine keeps agent execution. The client talks to it only through defined interfaces and does not fork it unless that is unavoidable.
  • R2 Modularity. Explicit modules with stated responsibilities and interfaces.
  • R3 Customization. Appearance, behavior, layout, commands, keybindings and settings.
  • R4 Ecosystem. Create, distribute, install, update, enable, disable and remove community extensions.
  • R5 Composable UI. Independently developed modules, shared tokens and primitives, replaceable panels and layouts.
  • R6 Safety. Third-party code must not silently gain filesystem, command, network or agent access.
  • R7 Upgrade resilience. OpenCode upgrades must not routinely break the client or its extensions.
  • R8 More surfaces later. Web and mobile follow once the desktop works, and they should reuse the same core rather than fork it.
  • R9 User-installed engine. Users install OpenCode themselves. The client ships no engine binary.

4.2 Quality attributes, in priority order

RecommendationWhen goals conflict, resolve them in this order:

  1. User control and security. An AI agent with tool access magnifies any extension compromise.
  2. Correctness of agent state. The user must never act on a stale or wrong picture of what the agent did.
  3. Upgrade resilience against a fast-moving engine.
  4. Extensibility.
  5. Performance and memory.
  6. Initial delivery speed.

05Architecture alternatives

Four realistic approaches. The comparison rates each criterion from your point of view: green is favorable, amber is mixed, red is unfavorable.

  1. Monolith with internal modules. One app with folders and conventions. No third-party code. OpenChamber's core looks like this.
  2. Modular core with a formal in-process extension API. Extensions load as code into the renderer and render native components. Obsidian works this way. VS Code is similar, with its extension host in a separate process but unsandboxed.
  3. Plugin-oriented, everything is a plugin, one trust level. Core features and third-party features use the same API. OpenCode's own gui-extensions works this way for built-ins, and its .ocdx groundwork extends the same trust to installed archives.
  4. Hybrid. A stable core, first-party feature modules on an internal SDK, a separate public API with sandboxed tiers, and engine plugins for agent-side work.

Verdict

RecommendationChoose approach 4, built in stages. Start where approach 3 is strongest: first-party features as modules on an internal SDK, the way OpenCode's own app proves out. That gives you the boundaries and the contribution registries without promising anything publicly. Publish a declarative tier as soon as the registries settle, since it is safe and covers most customization. Add sandboxed code extensions only after the first-party modules have shown which contribution points matter. Keep the internal SDK and the public API as separate surfaces permanently. That separation is what lets the internal side change every release while extensions keep working.

Approach 2 is the main temptation, because rich native extensions attract authors quickly. It is the wrong default here. An extension running in your renderer can reach the store, the DOM and every command, and in an agent client that adds up to sending prompts and approving tool runs. Offer that level of access later as an explicit trusted tier, never as the baseline.

6.6 Lifecycles

Application start and stop

  1. Main opens the client database, runs migrations and reads extension manifests. No extension code runs at this point.
  2. Main shows a window skeleton at once and starts gateway discovery in parallel.
  3. The renderer boots the core, sets up first-party modules synchronously (contributions only, no engine calls) and merges declarative extension contributions.
  4. The gateway discovers the engine, starts one if policy allows, checks version and capabilities, then opens the event stream.
  5. On server.connected, windows hydrate visible state and the onEngineConnected activation event fires.
  6. Sandboxed extensions activate lazily on their declared events.
  7. On quit: deactivate extensions with a time limit, flush stores, close streams. Never stop the shared engine.

Modules

First-party modules use the liveness model upstream already proved: pending, active, or inactive because the module is restarting, disabled, failed or blocked. Optional dependencies arrive as a live value that degrades gracefully. Required dependencies block setup until the provider returns. Everything a module registers is withdrawn when it leaves the active state. Setup is synchronous, and async work runs in owned tasks that check an abort signal after every await.

RecommendationUpstream ties these lifetimes to Solid's ownership tree. React has no equivalent, so make them explicit. ctx.add returns a disposable, each module instance owns a disposal scope and an AbortSignal, and the host disposes the scope when the module leaves the active state. Components reach the module context through a hook such as useModule().

6.11 React implementation notes

Streaming deltas are the one place React needs care. A naive store re-renders the whole timeline on every token. These patterns keep updates local:

  • Keep state outside React. The adapter writes to a plain store, normalized by id. Components subscribe through useSyncExternalStore with narrow selectors, so a delta to one text part re-renders only that part.
  • Batch by frame. The gateway already batches events (upstream uses 10 ms, OpenChamber 50 ms). Apply each batch once per animation frame.
  • Stream into a leaf. Render streaming text in a small component keyed by part id. Re-parse only the trailing Markdown block while it streams, and treat finished blocks as immutable.
  • Virtualize long timelines with a windowing library such as TanStack Virtual, which OpenChamber uses.
  • Keep fast-changing values out of context. Context suits rarely changing values like theme and the module context, not live session data.
// Subscribe one component to one timeline part; other parts never re-render.
export function usePart(sessionId: SessionId, partId: PartId) {
  return useSyncExternalStore(
    (notify) => timeline.subscribe(sessionId, partId, notify),
    () => timeline.part(sessionId, partId),
  )
}

function StreamingText(props: { sessionId: SessionId; partId: PartId }) {
  const part = usePart(props.sessionId, props.partId)
  return <Markdown source={part.text} streaming={part.state === "streaming"} />
}

7.3 Discovery and loading

  1. Main scans three roots: bundled extensions, the user extensions directory under app data, and developer folders registered in developer mode.
  2. It validates each manifest against the schema for its apiVersion, checks engines, and checks recorded file hashes for installed packages.
  3. Declarative contributions are merged into the registries before the first frame. No code loads at this stage.
  4. Code loads only when an activation event fires. Main serves package files from app-ext://<id>/ with a per-extension CSP header. On the web, the gateway server serves them from a separate origin instead (6.10).

7.4 Activation and lifecycle

Activation events: onCommand:<id>, onView:<id>, onAction:<id>, onEngineConnected, onSessionOpened, onToolCall:<pattern>, onUri. There is no onStartup for third parties, because startup time is shared by everyone.

7.7 Dependencies and compatibility

  • RecommendationIn Phase 3, support no inter-extension dependencies. Extensions share functionality through commands, which are already public and late-bound.
  • When demand appears, add requires and uses with upstream's semantics: a missing required provider blocks the extension, a missing optional provider degrades it. Resolve with semver ranges, activate in topological order, and reject cycles at install.
  • Compatibility is checked at install and at every app or engine version change. An incompatible extension is disabled with an explanation, never half-loaded.

7.8 Storage and scoped settings

  • Storage scopes are global, project (keyed by the engine's project id) and session. Starting quotas can follow OpenChamber's tested limits: 64 KiB per value and 2 MiB per namespace.
  • host.secrets stores per-extension secrets in the OS keychain through main.
  • Settings come from the contributed schema, are edited in the settings UI, and are read with host.settings.get and onChange. An extension can never read another extension's namespace.
  • Data survives disable and update. Uninstall removes it after a grace period unless the user chooses to purge it.

7.9 Error isolation and crash handling

  • A failing view affects only its frame. The host draws the frame and shows an error state inside it.
  • Every API call has a timeout. A background invocation has a total time limit (OpenChamber uses 20 s).
  • A contribution that throws renders nothing and records the error, which is upstream's rule for built-ins.
  • Repeated faults disable the extension automatically and tell the user why.
  • A safe-mode launch flag disables every non-bundled extension. It is the recovery path when an extension breaks startup.
  • The extension manager shows per-extension logs, the last error, activation time and memory.

7.10 Sandbox implementation in Electron

  • Windows run with sandbox: true, contextIsolation: true and no Node integration, as upstream's desktop does.
  • Extension frames use sandbox="allow-scripts" without allow-same-origin. That gives them an opaque origin with no access to the parent DOM, cookies or storage.
  • Files are served from app-ext://<id>/ with default-src 'none', scripts and styles limited to the package, and connect-src 'none'. All input and output goes through the host bridge.
  • Main denies navigation, new windows and all device permission requests that come from extension frames.
  • Open questionWhether Electron's site isolation puts these opaque-origin frames in separate renderer processes needs a measurement in the prototype. If they share the host's process, a renderer exploit in an extension frame reaches the host. The fallback is a WebContentsView per untrusted extension, at a higher memory cost.

7.13 Install, update, removal and rollback

  • Package: a zip with package.json at the root and built files only. Validate it before it replaces anything.
  • Layout: extensions/<id>/<version>/, with the current version recorded in the client database. Keep the previous version.
  • Update: download, validate, compare capabilities, ask for approval if they widened, switch the version pointer atomically, then reactivate.
  • Rollback: switch the pointer back. Data is untouched, because storage is keyed by id, not version.
  • Removal: deactivate, delete files, schedule data deletion.
  • Sources: local folder (developer mode, hot reload), zip file, URL, then index entries.

7.14 Distribution, staged

  1. Local: folder and zip installs, plus a developer mode that reloads on change.
  2. Curated index: a public git repository of JSON entries with id, versions, download URL, SHA-256 and publisher. Changes arrive by pull request with review. This is cheap to run and leaves an audit trail.
  3. Hosted registry: publisher accounts, signing, automated scanning, yank and deprecation, abuse reports and download counts. Open VSX is a reference for running a neutral registry.

08OpenCode compatibility and upgrade strategy

8.1 What the adapter contains

  • The only imports of @opencode/client and @opencode/schema in the codebase.
  • Domain mapping for reads and writes, and pure event translation.
  • Capability flags and version shims, so every "if the engine is older than X" decision lives in one file.
  • Contract fixtures for each supported engine version.

8.2 Detecting version and capabilities

  1. GET /api/info: read version and capabilities. A 404 means an incompatible protocol, as in the client's own probe.
  2. GET /openapi.json, cached per version: derive which operation ids and request fields exist.
  3. Compute EngineCapabilities and the support state (supported, untested or unsupported) against the declared range.
  4. Publish capabilities to the store. Modules and the extension API read flags. They never compare version strings.

8.3 Supported range

RecommendationStart with >=2.0.20 <2.1.0. The floor matches OpenChamber's tested floor, and everything after it has been additive (2.10). Patch versions newer than the latest one you tested run with an "untested engine" notice, and features whose capabilities are missing stay off. Raise the floor deliberately, never by accident.

8.4 Handling change

  • Reads: decode leniently. Ignore unknown fields, map unknown enum values to an unknown variant, and count unknown event types.
  • Writes: send a field only when the connected engine's schema declares it, because bodies reject unknown fields.
  • Experimental routes: behind feature flags that are off by default. Never exposed through the public extension API.
  • Deprecations: shims in the adapter, with a removal date tied to raising the supported floor.
  • New engine features: added behind a capability flag first, so older engines keep working.

8.5 Never rely on

  • The engine database, its tables or its migration state. OpenChamber's kv write is the cautionary example.
  • CLI-private files other than the registration file read through @opencode/client/service.
  • Data-directory layout, such as worktree paths.
  • Event ordering beyond the per-aggregate seq of durable events, or the size of streaming deltas.
  • Error message text. Use the typed error tags.
  • Timing, such as how long lazy directory initialization takes.
  • @opencode/client/solid internals, the private gui-extensions SDK, or the official desktop's IPC.

12Architecture decision records

ADR-001

Integrate only through public engine interfaces

Proposed
Context
The engine changes fast, and an audited public HTTP contract exists. Engine storage and CLI files are internal, and OpenChamber shows the cost of depending on them.
Decision
Use only the HTTP API, SSE, PTY sockets, plugin RPC, the registration file through @opencode/client/service, and published packages. No fork.
Alternatives
Fork the engine. Embed the engine through @opencode/sdk. Read engine storage directly.
Consequences
Some features wait for upstream. Upgrades stay cheap, and you never risk user data.
ADR-002

Join the shared service; never replace it unasked

Proposed
Context
One service per user; official clients replace other versions; two engines on one database are likely unsafe.
Decision
Discover and join without a version pin. Start the service with the user's installed CLI only when none is running. Ship no engine binary. Restart only with consent. Isolated mode always uses its own database.
Alternatives
Always spawn a private engine (OpenChamber). Pin and replace (the official desktop). Bundle a CLI.
Consequences
You must support a version range and handle engines you did not choose. Sessions are shared with the TUI and the official app.
ADR-003

Engine gateway in the Electron main process

Proposed
Context
Credentials must stay out of renderers. CORS refuses custom schemes. Several windows would multiply SSE subscriptions and the risk of overflow.
Decision
Main owns discovery, credentials, one stream per server and request forwarding, with no domain logic. The logic lives in @app/gateway-core, which imports no Electron, so a Node server can host it for web and mobile.
Alternatives
Renderer connects directly. A separate local server process from the start (OpenChamber).
Consequences
One extra IPC hop per request. A little discipline now; no gateway rewrite when web and mobile arrive.
ADR-004

Adapter package as the only OpenCode-aware code

Proposed
Context
Wire shapes change across releases. Features and extensions must not change with them.
Decision
@app/engine-opencode alone imports @opencode/*, maps to a client-owned domain model and exposes capability flags.
Alternatives
Use generated types everywhere. Depend on @opencode/client/solid as the store.
Consequences
A mapping layer to maintain. Engine upgrades touch one package.
ADR-005

Electron for the desktop shell

Proposed
Context
Service discovery ships as Node code. Extensions need a consistent web platform. Upstream and OpenChamber both use Electron.
Decision
Electron, with sandboxed renderers and utilityProcess available for later tiers.
Alternatives
Tauri: smaller, but discovery would need porting or a sidecar, and system webviews differ across platforms.
Consequences
Larger binaries and memory. One rendering engine for every extension author.
ADR-006

React for the host UI; framework-neutral extension API

Decided
Context
Solid's advantages here were reuse of upstream's Solid packages and fine-grained updates for streaming. The first is small, because this design already avoids depending on @opencode/client/solid and treats @opencode/ui as optional. The second has known React solutions. The owner prefers React, and web and mobile are planned.
Decision
React for first-party code. The public extension API exposes no framework types, so third-party authors can use anything inside their frames.
Alternatives
Solid, closer to upstream's code and cheaper per streamed token.
Consequences
Your own design system instead of @opencode/ui. Explicit module lifetimes and streaming patterns (6.6, 6.11). A larger contributor pool, OpenChamber's React code as nearby reference, and both Capacitor and React Native kept open for mobile.
ADR-007

First-party features as modules on an internal SDK

Proposed
Context
Upstream proved the pattern at scale: a manifest, tokens, liveness, declared stores, and a host that never names a module.
Decision
Every feature is a module with provides, uses and requires, contributing through registries and enforced by lint.
Alternatives
Feature folders by convention (OpenChamber).
Consequences
More ceremony per feature. Missing contribution points surface before the public API freezes.
ADR-008

Two APIs: internal module SDK and public extension API

Proposed
Context
An API that serves both first-party and third-party code turns the whole app into a public contract.
Decision
The internal SDK is unstable, in-process and framework-bound. The public API is versioned, async, serializable and capability-gated.
Alternatives
One shared API, as in gui-extensions with .ocdx.
Consequences
Two surfaces to document. Internals stay free to change.
ADR-009

Staged extension tiers

Proposed
Context
Most customization needs no code, and code from strangers is the main risk.
Decision
Declarative first, sandboxed iframes second, privileged services last. Agent capabilities go into OpenCode engine plugins.
Alternatives

Proposed

Proposed

Alternatives

Consequences

ADR-013

Distribution starts as a curated git index you maintain

Decided
Context
A hosted registry needs accounts, signing, scanning and abuse handling. None of that pays off before there are real publishers.
Decision
A public git repository of index entries (id, versions, download URL, SHA-256, publisher, declared capabilities). Entries arrive by pull request and you review them against written rules. The client reads the index and can hide a yanked version remotely.
Alternatives
npm as the registry. A hosted registry from day one. Open VSX.
Consequences
Review work scales with submissions. Moving to a hosted registry later keeps the same index format.
ADR-014

Web and mobile reuse the desktop core

Proposed
Context
Web and mobile follow the desktop. Rewriting UI or gateway per surface would double maintenance.
Decision
One React UI and one gateway core. Web adds a server host with its own login. Mobile wraps the web build in Capacitor.
Alternatives
React Native for mobile. Separate web product.
Consequences
Mobile feels web-based rather than fully native. Extension sandboxing works the same everywhere.
